## 3. Invariant Alignment

| Invariant | Relevance to Artix Qualification |
|-----------|-----------------------------------|
| **M-01** | Migration is target-state driven: Qualification docs define desired init-system state, not mandatory sequential release replay. |
| **M-02** | Evolution history is immutable: `EVT-ARTIX-001` commit hash proves Artix transition rules cannot be silently modified. |
| **M-03** | Migration intelligence is versioned independently: `TC18` transition catalog references Artix rules by stable identifier, not engine version. |
| **M-04** | The actual installation is authoritative: Qualification tests validate against the running system's init implementation (runit vs openrc), not OS release number. |
| **M-05** | Migrations are staged: Test logs show pre-transition validation (`test_run_001.log`) before switching init system. |
| **M-06** | Migration operations must be recoverable: Compensating procedures journaled in `test_run_002.log` enable rollback to pre-qualification state. |
| **M-07** | Historical artifacts are archived: Comparison matrix and ledger entries are stored in `evidence/artix/` with content hashes. |
| **M-09** | Migration must be repeatable: Test IDs (`ARTIX-RUNIT-Q001`, etc.) allow re-execution without uncontrolled duplication. |
